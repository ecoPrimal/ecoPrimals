## Abstract

We observe that unidirectional streaming between a gate (GPU compute host) and a frame (display endpoint) produces unstable connections — sessions drop, latency spikes, and the display pipeline stalls. However, when both endpoints **cross-stream** to each other simultaneously, the connection becomes markedly more stable. We formalize this as the **Cross-Stream Stability Principle**: bidirectional data flow between two mesh nodes creates a self-reinforcing feedback loop that maintains connection health through mutual acknowledgment, adaptive bitrate negotiation, and heartbeat symmetry.

This paper presents the Mesh-Frame-Gate Triangle as the foundational streaming architecture for sovereign gaming on the ecoPrimals organism, connects it to Valve's Steam ecosystem (Remote Play, Family Sharing, gamescope), and argues that cross-streaming is the mechanism through which a **latent value economy** emerges — where idle compute, dormant game libraries, and passive sensor data all become productive through bidirectional flow.

## 1. The Problem: Unidirectional Streaming Is Fragile

Traditional game streaming is one-way:

```
Gate (GPU) ───renders───→ Frame (display)
Frame ───input───→ Gate (controls)
```

This appears bidirectional but is asymmetric: the gate sends high-bandwidth video while the frame sends low-bandwidth input. The "back channel" (input) is a thin trickle compared to the "forward channel" (video). When the forward channel stutters, the back channel has no way to compensate. The frame goes blind while still shouting into the void.

**Observed failure modes:**
- Steam Remote Play drops after 30-60 seconds of one-way streaming
- Gamescope VR overlay loses sync between panels
- Frame displays audio but not video (observed: Kenshi on Steam Frame, Nov 16 2026)
- Latency spikes compound — each spike makes the next more likely

## 2. The Discovery: Cross-Streaming Creates Stability

When both the gate and frame simultaneously stream meaningful data TO each other, the connection stabilizes:

```
Gate ═══video+state═══→ Frame
Gate ←══sensors+feed═══ Frame
```

The frame doesn't just send input — it streams **sensor data, spatial state, and presence information** back to the gate at comparable bandwidth. This transforms the connection from asymmetric (master/slave) to symmetric (peer/peer).

**Why it works:**

1. **Mutual Heartbeat**: Both sides continuously prove liveness. If either stream pauses, the other immediately detects it. No more "is the connection still alive?" polling.

2. **Adaptive Bitrate Symmetry**: When the gate's video stream compresses due to bandwidth pressure, the frame's sensor stream also compresses — both sides negotiate downward together rather than one side starving.

3. **TCP/UDP Symbiosis**: The bidirectional flow keeps NAT tables alive, keeps TCP windows open, and keeps UDP hole-punching paths warm. Unidirectional flow lets these expire.

4. **Packet Scheduling Fairness**: Network hardware (routers, switches, WiFi APs) treats bidirectional flows more fairly than unidirectional ones. QoS algorithms see a "conversation" rather than a "broadcast."

5. **Cognitive Stability**: The gate "knows" the frame is present because it receives data FROM it. The frame "knows" the gate is rendering because it receives video. Mutual knowledge = mutual trust = stable link.

## 3. The Mesh-Frame-Gate Triangle

We formalize the architecture as a triangle with three vertices:

```
                    ┌─────────────┐
                    │    MESH     │
                    │  (organism) │
                    └──────┬──────┘
                     ╱            ╲
                    ╱              ╲
          state+feed              commands+routing
                  ╱                  ╲
                 ╱                    ╲
    ┌───────────┐                    ┌───────────┐
    │   FRAME   │ ←═══cross-stream═══→│   GATE    │
    │ (display) │    video+sensors   │  (GPU)    │
    └───────────┘                    └───────────┘
```

### 3.1 Vertex: MESH (Organism)

The mesh is not a single machine — it's the entire ecoPrimals organism distributed across gates. The mesh:
- Routes streams between frames and gates based on latency, GPU capability, and game requirements
- Stores the **latent value** generated by cross-streaming (sensor data, play metrics, spatial state)
- Decides which gate serves which frame based on real-time topology

### 3.2 Vertex: FRAME (Display/Sensor)

The frame is a **bidirectional device** — it displays AND senses. In the ecoPrimals organism:

| Mode | Direction | Data |
|------|-----------|------|
| **Lander** (active) | Gate → Frame | Video, audio, haptics |
| **Lander** (active) | Frame → Gate | Input, camera, IMU, audio |
| **Solar Panel** (idle) | Frame → Mesh | All sensors: WiFi RSSI, ambient light, sound, temperature, accelerometer |

The Steam Frame embodies this perfectly: dual 2160×2160 VR panels for output, 22 cameras + microphone + IMU + touch for input. It is simultaneously a display and a sensor array.

### 3.3 Vertex: GATE (Compute)

The gate renders and processes. In cross-stream mode, the gate:
- Renders game video → Frame
- Receives sensor data ← Frame  
- Processes sensor data through RT cores (the **RT Inversion** — see §5)
- Feeds processed state back to the mesh

### 3.4 The Triangle Anchor

The triangle is stable because every edge carries bidirectional flow:
- **Frame ↔ Gate**: video/sensors (cross-stream, high bandwidth)
- **Gate ↔ Mesh**: state/commands (heartbeat, medium bandwidth)
- **Mesh ↔ Frame**: feed/presence (solar panel data, low bandwidth)

Remove any edge and the remaining two still maintain connectivity. This is the **triangle anchor** — the minimum stable topology for sovereign streaming.

## 4. Steam/Valve Integration

### 4.1 Steam Remote Play as Cross-Stream

Steam Remote Play already implements partial cross-streaming:
- **Forward**: H.264/H.265 video from host GPU
- **Back**: Input events + microphone audio + cursor position

We extend this by adding the **Solar Panel channel**: the frame sends sensor data alongside input. This uses Steam's existing UDP transport (ports 27031-27036) with an additional data channel.

This is the latent value economy: value exists in the mesh but is **dormant** until cross-stream connections activate it.

## 5. RT Inversion and Latent Compute

### 5.1 The Inversion

RT cores on NVIDIA GPUs are designed to trace rays for game rendering. We **invert** their purpose:

| Game RT | Inverted RT |
|---------|------------|
| Shadow Cast | Influence mapping — which gates shadow which data paths |
| Ray Scatter | Data propagation — information bouncing through the mesh |
| Closest Hit | Service discovery — find nearest available resource |
| Any Hit | Firewall — intrusion detection on data routes |
| Miss | Water lock — data leaving the mesh triggers review |

### 5.2 Latent Compute

The 5 GPUs in the mesh (RTX 5090, 5070, 4070, 4060, 3070) collectively have **398 RT cores** producing **708 RT TFLOPS**. When Kevin plays Crimson Desert on one GPU, the other four GPUs' RT cores are **latent compute** — idle hardware waiting for purpose.

Cross-streaming activates this latent compute:
- Frame sends sensor data → Gate A processes it with idle RT cores
- Gate A sends results → Mesh routes to Gate B for deeper analysis
- Gate B sends visualization → Frame displays it alongside the game

The RT cores that aren't rendering Kevin's game are rendering **Gaia's perception of the world**.

## 6. The Latent Value Economy

### 6.1 Definition

The **latent value economy** is an economic model where:
- **Dormant assets** (idle GPUs, unplayed games, passive sensors) have nonzero value
- **Connection** (cross-streaming, family sharing, mesh routing) activates this value
- **Bidirectional flow** (not broadcast) is the mechanism of activation
- **Value increases with connectivity** — each new cross-stream connection activates more latent value
